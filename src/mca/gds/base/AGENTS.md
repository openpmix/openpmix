# AGENTS.md: The GDS framework base

This is the `gds` framework's own infrastructure — **not a component**.
Read the framework [`AGENTS.md`](../AGENTS.md) first: the assign-on-demand
selection model, the module interface, and the `PMIX_GDS_*` routing macros
all come from there. This file covers only what lives in this directory:
four files, three of which are small, and one routine that every component
depends on.

## Files

| File | Contents |
|------|----------|
| [`base.h`](base.h) | the internal base API — `pmix_gds_globals`, the active-module wrapper class, the modex blob-info flags, and the exported helpers below |
| [`gds_base_frame.c`](gds_base_frame.c) | `PMIX_MCA_BASE_FRAMEWORK_DECLARE`, the globals, `pmix_gds_open`/`pmix_gds_close`, and the `pmix_gds_base_active_module_t` class instance |
| [`gds_base_select.c`](gds_base_select.c) | `pmix_gds_base_select()` — query every component, init each returned module, build the priority-ordered `actives` list |
| [`gds_base_fns.c`](gds_base_fns.c) | the five exported helpers: available-modules, assign-module, fallback-module, setup-fork, store-modex, plus `pmix_gds_base_proc_array_id()` |

`static-components.h` is generated by `configure`; never edit it.

## The framework declares no MCA parameters

`PMIX_MCA_BASE_FRAMEWORK_DECLARE(pmix, gds, "PMIx Generalized Data Store",
NULL, pmix_gds_open, pmix_gds_close, ...)` — the fourth argument is the
register function, and it is `NULL`. Every `gds` MCA parameter in the tree
belongs to the `shmem3` component. If you add a framework-level parameter,
that argument has to become a real function; adding
`pmix_mca_base_var_register()` calls to `pmix_gds_open` instead is the
wrong place (see [`../../base/AGENTS.md`](../../base/AGENTS.md)).

`pmix_gds_open` constructs `actives`, sets `initialized`, and opens the
components; `pmix_gds_close` finalizes each active module, tears the list
down, frees `all_mods` and closes the components. Both are re-entrant
across an init/finalize cycle in one process — a tool or a test can call
`PMIx_Init` more than once — so anything either of them touches has to be
left in a state the other can start from.

## Selection

`pmix_gds_base_select(info, ninfo)` runs once, guarded by
`pmix_gds_globals.selected`. It queries each component, calls the returned
module's `init` (dropping any that refuses), wraps the survivors in
`pmix_gds_base_active_module_t { pri, module, component }`, and inserts
them into `actives` in **descending priority order**. Zero survivors is a
fatal condition for this framework: it raises the `no-plugins` `show_help`
topic from `help-pmix-runtime.txt` and returns `PMIX_ERR_SILENT`.

Two things about that function are easy to get wrong:

- **The `selected` guard is cleared again on the zero-module path.**
  Leaving it set means a later, better-placed attempt is refused without
  trying — the framework reports "already selected" for a state in which
  nothing was.
- **`actives` is the menu, not a choice.** Nothing here decides which
  module serves a peer; the ordering only seeds the default bid. See
  `assign_module` below.

`all_mods` — the comma-delimited, priority-ordered list of module names —
is built here and handed to peers through the `ptl` handshake, which is
how a client learns what the server can offer.

## The exported helpers (`gds_base_fns.c`)

```c
char *pmix_gds_base_get_available_modules(void);
pmix_gds_base_module_t *pmix_gds_base_assign_module(pmix_info_t *info, size_t ninfo);
pmix_gds_base_module_t *pmix_gds_base_get_fallback_module(pmix_gds_base_module_t *failing);
pmix_status_t pmix_gds_base_setup_fork(const pmix_proc_t *proc, char ***env);
pmix_status_t pmix_gds_base_store_modex(pmix_buffer_t *buff,
                                        pmix_gds_base_store_modex_cb_fn_t cb_fn,
                                        void *cbdata);
pmix_status_t pmix_gds_base_proc_array_id(const pmix_info_t *array, size_t size,
                                          pmix_rank_t *rank, size_t *idpos);
```

Each is `PMIX_EXPORT`ed; the components' own symbols are not, which is
why the unit tests reach this directory directly and the components only
through the macros.

- **`assign_module`** walks `actives`, calls each module's
  `assign_module(info, ninfo, &pri)` and keeps the highest bid; a module
  returning `pri < 0` falls back to its component priority. **It must
  always return a module** when any is active — every shipped module offers
  itself unconditionally, and a named module only raises *its own* bid. A
  `PMIX_GDS_MODULE` directive naming something unknown, or carrying a value
  that is not a usable string, still has to resolve. `test/unit/gds_datastore`
  holds that line.
- **`get_fallback_module`** returns the highest-priority active module whose
  name differs from the failing one, selecting purely by the recorded
  component priority — it does **not** consult `assign_module`, and no
  module names are hard-coded. This is what the client-side GDS fallback
  uses; `test/unit/gds_fallback` covers it, including the "never returns the
  module it was told is failing" property.
- **`setup_fork`** is a fan-out across every active module, tolerating
  `PMIX_ERR_NOT_AVAILABLE` from a module that has nothing to contribute.
- **`proc_array_id`** finds the identifier a `PMIX_PROC_INFO_ARRAY` uses.
  The Standard lets a host identify the process with `PMIX_RANK` or
  `PMIX_PROCID`, in any position; this scans for whichever was used,
  preferring `PMIX_RANK`, and returns the array index that carried it so
  the caller can skip it when storing the rest. Covered by
  `test/unit/proc_array_id`.

## `pmix_gds_base_store_modex` — the envelope walker

This is the one substantial routine here, and both components' `store_modex`
delegate to it. It exists so neither component reimplements the wire
structure of an aggregated fence result. That structure is nested three
deep:

```
buff
 └── PMIX_BYTE_OBJECT   one per contributing server
      ├── bool          was the rank-level block compressed?
      └── PMIX_BYTE_OBJECT   the rank-level block (pmix_compress if flagged)
           ├── byte     the collect flag for that node
           └── PMIX_BYTE_OBJECT   one per contributing proc
                └── pmix_proc_t followed by that proc's pmix_kval_t's
```

The walker decompresses where flagged, checks the collect flag is the same
across servers (otherwise the `collection-mismatch` topic in
`help-pmix-server.txt` fires and it returns `PMIX_ERR_BAD_PARAM`), calls
`cb_fn(&proc, &pbkt)` once per proc blob, and finally calls
`cb_fn(&proc, NULL)` once per **nspace** that appeared, to signal "done".

### The callback contract, which is not obvious and has been broken

**`cb_fn` must return `PMIX_SUCCESS` for a blob it consumed.** The walker
treats any other status as a failure of the server contribution it is
walking: it logs the error and stops, abandoning the remaining procs in
that contribution. It then converts `PMIX_ERR_UNPACK_READ_PAST_END_OF_BUFFER`
to `PMIX_SUCCESS` for its own caller — so a callback that returns the
unpack "ran off the end" code, which is exactly how a callback knows it has
finished a blob, produces a modex that silently contains only the *first*
proc of each contribution while reporting success. That is not
hypothetical; `shmem3`'s callback did it. Convert the code inside the
callback, as `hash`'s does.

`test/unit/gds_datastore` builds a synthetic envelope and asserts both
halves of this: every proc blob is delivered and done is signalled once per
nspace, and a callback that reports a non-success status truncates the
walk.

Two other things to keep in mind if you touch it:

- The `cbdata` is a `pmix_server_trkr_t *` and its `collect_type` is read
  before anything else, to decide whether an empty payload is an error.
- The outer loop is effectively single-pass: the inner loop already
  consumes the next server-level blob from `buff` before it re-tests. Do
  not "fix" the outer loop into doing work; it is the termination check.

## Core data in `base.h`

- **`pmix_gds_globals`** — `actives`, `initialized`, `selected`, `all_mods`.
- **`pmix_gds_base_active_module_t`** — one entry on `actives`, pairing a
  module with the priority it was inserted at and its component.
- **`pmix_gds_modex_key_fmt_t`** (`NATIVE_FMT` / `KEYMAP_FMT`) and the
  `PMIX_GDS_COLLECT_BIT` / `PMIX_GDS_KEYMAP_BIT` blob-info flags, with the
  `PMIX_GDS_*_IS_SET` accessors — the encoding a modex reader uses to
  learn how keys were written and whether data was collected.

## When working here

- **Everything in this directory runs on the progress thread.** There is no
  caddy pattern anywhere in `gds`; the thread-shift happens above it, in
  the caller. See the Threading section of the framework doc.
- **A change to the envelope layout in `store_modex` is a wire-format
  change.** Peers built from different releases exchange these blobs.
  Treat the layout as append-only per the top-level interoperability rules.
- **The helpers here are `PMIX_EXPORT`ed and the components' are not.**
  That is why `test/unit/gds_datastore` and `test/unit/gds_fallback` can
  test this directory directly but have to reach the components through
  the `PMIX_GDS_*` macros and the public server API.
